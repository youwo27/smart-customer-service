## 1. 问题定义

### 业务问题（一句话）

家居电商 3 平台（天猫/抖音/小程序）月咨询量 3 万条，80% 是重复常见问题（退货/物流/优惠券），但 8 个客服三班倒仍响应慢，且夜间无人值守，差评集中在"回复慢""半夜没人"。

### 当前不用 AI 怎么解决

| 方式 | 现状 | 问题 |
|------|------|------|
| 人工客服 | 8 人 3 班倒 | 成本高（8 人 × 3 班）、非 24/7、高峰期排队 |
| 旧版"智能客服"（第三方） | 关键词匹配 | 答非所问，是差评来源之一 |
| 静态 FAQ 页面 | 无交互 | 用户找不到答案就流失，体验差 |

### 用 Agent 解决的 ROI

- 常见问题自动解决率预期 **≥ 60%** → 人工工时减少约 **30%**（8 人 → 约 6 人当量）
- 平均响应时间 **3min → ≤ 5s**
- **夜间自动兜底**：解决"半夜没人"的差评来源
- 人工客服只处理：复杂问题、高危操作、情绪激烈用户

## 3. 边界定义

### Agent 负责什么？

**自动回复类**
- 知识库问答：退货政策、物流说明、优惠券规则、商品咨询（走 RAG 检索）
- 意图识别：查物流 / 退换货 / 价保 / 投诉 / 商品咨询 / 闲聊

**查询类（工具调用）**
- `query_order`：查询订单状态
- `query_logistics`：查询物流轨迹
- 优惠券可用情况查询

**简单售后（工具调用，高危必须人工）**
- 退换货申请**录入**（仅登记，不直接执行退款）
- 开票申请登记
- 地址修改（需二次确认）

### Agent 不负责什么？（硬边界）

| 场景 | 处理 | 原因 |
|------|------|------|
| 赔偿金承诺 | **一律转人工**，AI 绝不答应 | 法律/成本风险 |
| 退款/赔付金额 > ¥500 | 必须人工审批（HITL） | 金额阈值 |
| 用户情绪激烈（辱骂/刷屏/威胁） | 自动转人工 + 记录会话 | 升级策略 |
| 敏感信息操作（改支付方式/注销账号） | 转人工 | 隐私安全 |
| 法律/合规声明 | 转人工 | 合规风险 |
| 确定性计算（运费精确计算/价保计算） | 走规则引擎，不走 LLM | 准确率 |
| 夜间（23:00-次日 8:00）AI 搞不定 | 转人工队列/留言 | 无人值守兜底 |

### 什么情况回退到人工/规则系统？

- Agent 连续 2 次检索后仍无法回答
- 用户明确要求"转人工"/"找客服"/"投诉"
- 高危操作审批超时（30s 无人工响应 → 拒绝并通知用户）
- LLM 输出被安全审核拦截
- 检测到辱骂/威胁情绪

## 4. 失败模式分析

| # | 失败场景 | 处理策略 | 优先级 |
|---|---------|---------|--------|
| 1 | AI 误答赔偿/金额承诺 | 高危词实时拦截 + 强制转人工 + 审计日志 | P0 |
| 2 | 大额退款（>¥500）被误触发 | 规则层拦截 + HITL 人工审批 | P0 |
| 3 | 三平台接口格式不一致 | 适配器层统一格式（数据存取层封装） | P1 |
| 4 | 旧系统问答数据质量差 | 清洗 + 人工抽检，劣质数据不入库 | P1 |
| 5 | 用户发图片/订单号 | 一期不做图片理解，提示文字描述；订单号走查单工具 | P1 |
| 6 | LLM 故障（5xx） | 重试 ×3（指数退避）→ 切备用模型 → 仍失败转人工 | P0 |
| 7 | 上下文超窗口 | 触发压缩（摘要历史），禁止暴力截断 | P1 |
| 8 | 夜间无人可转 | 留言 + 次日优先处理，明确告知用户 | P1 |
| 9 | 成本超预算 | 模型路由（简单任务走小模型）+ 用量监控告警 | P1 |
| 10 | 并发过高内存溢出 | Semaphore 限流 + 请求排队 | P2 |

## 6. 系统架构（承接架构设计）

```
① 前端接入层：网页 / 聊天窗口 / 抖音淘宝 IM / 小程序 / API
② 网关调度层：鉴权、限流熔断、多渠道收口
③ Agent 应用层：意图识别 → ReAct 循环（检索层 + 工具层 + 人工转接触发器）
④ 领域业务服务层：订单 / 物流 / 售后工单 / 优惠价保（确定性逻辑不走 LLM）
⑤ 数据存取层：DAO / Redis / 向量库 / 第三方接口适配器
⑥ 基础设施层：MySQL / Redis / 向量库 / MQ / OSS / 监控 / LLM 服务
```
